§2 · Swimlane walkthrough

Same eleven steps, same six lanes as the As-Is map. Steps with no BRD requirement attached (1, 2, 5, 7) are unchanged from As-Is — this project's scope is the reporting/data-capture layer, not a full operational redesign, and it would be dishonest to claim a fix at a step nothing in the BRD actually touches.

Condition Monitoring — continuous background

PartialStep 0 — Condition monitoring. Changed by FR-07 and FR-08. An amber reading that persists for three consecutive review cycles now automatically raises a flag or scheduling prompt instead of silently rolling over in an inbox closes PP6. Every sensor now carries a logged last-calibration date, so a reviewer can tell a genuine precursor from a fouled/drifting sensor closes PP7 — though only as far as the calibration-logging discipline is actually kept up; a process fix, not a one-time data fix. PP11 (sub-threshold stoppages) is unchanged — no requirement touches it, and it's a permanent, disclosed scope boundary, not a gap this project failed to close.

Production / Operations

FixedStep 1 — Failure occurs / detected. Unchanged. No functional requirement targets detection itself.
FixedStep 2 — Breakdown reported & logged. Changed by FR-05. The work order now captures an explicit planned/unplanned flag at the moment it's raised, with a distinct field for a work order spanning both — the direct fix for the two-unsynchronised-clocks problem, because the ambiguity FR-05 removes is exactly what let the clocks drift apart unnoticed in the Financial Controller's crusher example.

Maintenance — Planning & Supervision

PartialStep 3 — Work order raised & triaged. FR-05's planned/unplanned flag helps here too. PP2 (the cause-code dropdown) is not fixed by anything currently in the BRD — see the new FR-14 proposal, §5.
Decided — Option BStep 4 — Prioritized & scheduled (the fast-fix/root-cause fork). Resolved 7 September 2026 — see §4. A repeat-failure escalation checkpoint is adopted: a further fast-fix on a repeat failure now needs documented joint sign-off from Maintenance and Reliability. FR-01's asset-level rollup feeds that sign-off with the evidence it needs. Option C (a reliability budget pool) is deferred to a future phase, not chosen now.

Maintenance — Execution & Condition Monitoring

FixedStep 5 — Diagnosed. Unchanged.
Fixed (minimum bar)Step 6 — Repaired. Changed by FR-06. At minimum, every work order now supports a flag for "crew was reassigned mid-repair," so the dead time can be subtracted out rather than silently inflating the recorded duration. The stretch-goal half of FR-06 (live start/stop timestamps) would close this more fully but isn't required for go-live.

Production / Operations (return to service)

Depends on Option BStep 7 — Returned to service. Unchanged directly, though it inherits whatever happened at Step 4 — if the new escalation checkpoint actually catches a repeat failure and a proper fix goes in, the loop back to Step 1 doesn't get triggered at all, which is the real measure of whether Option B is working.

Reliability Engineering

Depends on Option BStep 8 — Root cause analysis. Indirectly supported by FR-01, and now directly feeds Step 4's escalation checkpoint. The RCA itself isn't changed by any requirement, but the case it's arguing for now has real numbers behind it — an asset's cumulative failure/cost history — rather than, in the Reliability Engineer's words, "one bloke with a spreadsheet and a hunch." That evidence is exactly what a Step 4 sign-off decision now has to weigh — though it still doesn't touch the approval-pathway problem underneath it (PP10 stays open; only the deferred Option C would touch that).

CMMS / System of Record

Fixed (pending sign-off)Step 9 — Closed out & data captured. Changed by FR-09, pending Operations-side sign-off. A non-disciplinary contributing-factor field lets a closeout note "suspected operator-influenced" separately from the technical failure mode, closing PP8 — but only once an Operations stakeholder has actually reviewed the field, which hasn't happened yet. Also inherits FR-05's and FR-06's fixes finalising correctly here instead of the old, flawed way.

Leadership & Finance

FixedStep 10 — Reported & reviewed. The most heavily changed step — FR-01, FR-02, FR-03, FR-04, FR-10, FR-11, FR-12, FR-13 all land here. A user can pull up an asset's cumulative failure/cost history, see failure modes ranked by count and cost, see failure rate and cost by asset tier, see every figure tagged as dataset-derived / cited-source / labelled-assumption, see the preventable-vs-random split, the torque/tool-wear threshold result, and the precursor-pattern classification.
Depends on Option BStep 11 — Strategy & continuous improvement. Indirectly supported, same caveat as Step 8 — better information reaching this step doesn't by itself guarantee action gets taken; that now depends on how well Option B's checkpoint holds in practice, not on whether Step 4 gets redesigned at all — that part is decided.

§4 · Step 4 redesign — decision (resolved 7 September 2026)

Decision: Option B, for the current phase. A repeat-failure escalation checkpoint — once the same failure mode recurs on the same asset within a defined window, a further fast-fix requires documented joint sign-off from the Maintenance Manager and Reliability Engineer. Option C is deferred, not rejected — carried forward as a named future-phase recommendation in the Week 3 business case, pending Finance/capital-planning validation. Option A stays in place regardless, as already-committed decision support. The table below is kept as the record of the trade-off comparison that led here, not as a still-open menu. None of the three options touches PP10, the opex/capex approval-pathway mismatch — a real structural constraint outside a reporting project's ability to fix by redesigning a workflow step; only the deferred Option C would.

Still open, flagged honestly: the escalation window itself (e.g., "twice in 6 months") hasn't been validated with the Maintenance Manager or Reliability Engineer yet — a starting assumption, same category as the BRD's FR-07 amber-escalation threshold, and needs confirming before this becomes a real workflow rule rather than a placeholder concept.

§6 · New requirement surfaced by process mapping — FR-14 (proposed)

Finding: building the gap-analysis table above caught that PP2 (the cause-code dropdown) had been loosely attributed to FR-05 in this map's own earlier pain-point index — inaccurate; FR-05 covers only the planned/unplanned flag. There is no functional requirement anywhere in the BRD that redesigns the cause-code taxonomy.

Proposed FR-14 (Should) — Simplified, consistent cause-code taxonomy. Replace the current ~40-option list, roughly half of which don't fit real failure descriptions, with a smaller, mutually-exclusive set mapped to real failure modes.

Status: proposed, not yet written into the BRD. Logged in Scope-Decisions-and-Limitations-Log.md — folding it into a future BRD v3 is a decision for Gagana, same pattern as every other addition to this project's locked documents.
